# DOMA TECH — демонстрационный сайт

Опубликованная версия DOMA TECH — статический демонстрационный сайт для сравнения и подбора посудомоечных машин.

**Сайт:** https://marcostavar24633-cyber.github.io/doma-tech/

## Что реализовано

- Адаптивная витрина на русском языке.
- Категории посудомоечных машин.
- Демонстрационный подбор по параметрам.
- Примеры моделей с ориентировочными характеристиками и ценами.
- Локальные фильтры и сортировка каталога.
- Таблица сравнения моделей.
- Раскрывающиеся характеристики и FAQ.
- Демонстрационная форма без отправки и сохранения данных.
- Базовые средства доступности: клавиатурный фокус, skip-ссылка, подписи полей, reduced motion.

## Технологии и структура опубликованной версии

Публичная версия работает без backend и собирается из каталога `public/`.

- `public/index.html` — разметка страницы и SEO-метаданные.
- `public/styles.css` — стили и адаптивная верстка.
- `public/script.js` — интерактивность на стороне браузера.
- `public/favicon.svg` — иконка сайта.
- `.github/workflows/deploy-prototype.yml` — публикация на GitHub Pages.

## Локальный просмотр

Можно открыть `public/index.html` непосредственно в браузере. Для локального HTTP-просмотра из корня репозитория подойдёт любой статический сервер, например:

```bash
python -m http.server 8000 --directory public
```

Затем откройте `http://localhost:8000`.

## Публикация

Workflow GitHub Actions запускается при изменениях в `public/**` или в файле `.github/workflows/deploy-prototype.yml`. Он копирует содержимое `public/` в Pages artifact и публикует его через GitHub Pages.

Ручной запуск доступен через вкладку **Actions** репозитория.

## Ограничения демонстрационной версии

- Это не работающий интернет-магазин и не система приёма заказов.
- Формы не отправляют и не сохраняют введённые данные.
- В проекте не используются база данных, авторизация, серверное API или платёжная система в опубликованной версии.
- Цены и характеристики моделей приведены как справочные ориентиры; их нужно перепроверять у продавцов и по точной модификации.
- Наличие товаров, цены DOMA TECH, доставка, гарантия и условия продажи не подтверждены.
- Индексация поисковиками отключена через `noindex,follow` до реального запуска коммерческого проекта.

## Отдельная серверная заготовка в репозитории

В корне репозитория сохранены файлы серверной версии (`server.js`, `package.json`, `Dockerfile`, `docker-compose.yml`, `data/`, `uploads/` и `.env.example`). Они **не входят в публикацию GitHub Pages** и не используются текущей статической страницей.

Серверную заготовку нельзя считать готовой к коммерческому запуску только на основании наличия этих файлов. Перед её отдельным развёртыванием необходимы самостоятельная проверка безопасности, конфигурации, обработки персональных данных, резервного копирования и эксплуатационных требований. Не запускайте её на публичном сервере без такой проверки.

Docker-образ запускает Node.js от непривилегированного пользователя `node` и содержит healthcheck для `/api/health`. При использовании bind mounts `./data` и `./uploads` на хосте заранее создайте эти каталоги и назначьте им права записи для UID/GID пользователя контейнера (обычно `1000:1000`), иначе SQLite и загрузка изображений могут не работать. Docker-сборка и запуск после изменения ещё не тестировались.

## Перед коммерческим запуском

1. Подтвердить продавца, ассортимент, цены и наличие.
2. Указать реальные контакты и условия оплаты, доставки, возврата и гарантии.
3. Подготовить юридические документы и корректные согласия, если будут собираться персональные данные.
4. Решить, нужна ли серверная часть; не подключать её автоматически к статическому прототипу.
5. Провести браузерные тесты на мобильных устройствах, клавиатуре и с экранным диктором.
6. После готовности проверить SEO-метаданные и только затем снять `noindex`.

## Серверная заготовка: SQLite backup

Серверная часть в корне репозитория — отдельная заготовка и не используется GitHub Pages.

- Создать проверенную резервную копию: `npm run db:backup`.
- Восстановить копию: остановить приложение и выполнить `ALLOW_DB_RESTORE=true npm run db:restore -- ИМЯ_ФАЙЛА.sqlite`.
- Проверить обслуживание базы: `npm run test:db`.
- Полный набор проверок: `npm test`.

По умолчанию сохраняются 7 последних проверенных резервных копий. Количество можно задать переменной `BACKUP_RETENTION_COUNT` (целое число от 2 до 365). Ротация запускается только после создания, проверки целостности и сверки SHA-256 новой копии. Непроверенные или повреждённые архивы автоматически не удаляются.

Резервные копии хранятся локально в `backups/`; каталог исключён из Git. Для защиты от потери сервера или диска дополнительно требуется отдельное внешнее хранилище и регулярная проверка восстановления. Не храните единственную копию рядом с рабочей базой.

Восстановление требует остановленного приложения. Скрипт проверяет манифест и целостность источника. Если рабочая база уже существует, создаёт safety-copy перед заменой; если сервер новый и базы ещё нет, устанавливает проверенную копию как начальную. После восстановления приложение следует запустить в ограниченном режиме и проверить.

## Внешняя резервная копия (rclone)

Для независимого хранения можно использовать отдельное хранилище, поддерживаемое [rclone](https://rclone.org/). Установите rclone на сервере и настройте remote типа `crypt`, направленный на облачное хранилище. Не используйте незашифрованный remote для базы, содержащей учётные записи или заказы.

1. Создайте и проверьте локальную копию: `npm run db:backup`.
2. Установите переменную `OFFSITE_RCLONE_REMOTE=имя-crypt-remote:doma-tech`.
3. Передайте выбранную копию и её манифест: `npm run db:offsite -- ИМЯ_ФАЙЛА.sqlite`.

Скрипт повторно проверяет SHA-256, манифест и целостность SQLite до передачи. Он отправляет базу и JSON-манифест двумя отдельными операциями, затем выполняет `rclone check --download` для каждого файла, чтобы проверить содержимое удалённой копии чтением обратно. Скрипт не использует shell и не удаляет удалённые файлы. При ошибке передачи или проверки завершится с ненулевым кодом. После передачи проверяйте наличие обоих файлов в удалённом хранилище и периодически выполняйте тестовое восстановление из скачанной копии.

Пример настройки remote, пароль шифрования и облачные учётные данные храните вне репозитория — в защищённой конфигурации rclone или менеджере секретов. Не добавляйте их в GitHub, `.env.example`, логи или командные строки. Само наличие команды не означает, что внешнее хранилище настроено или что копия уже загружена.

### Скачать копию из внешнего хранилища

Перед скачиванием настройте тот же `OFFSITE_RCLONE_REMOTE`, что и для загрузки. Команда получает выбранную резервную копию и манифест во временный каталог, сверяет SHA-256 и проверяет целостность SQLite. Только после успешной проверки оба файла копируются в локальный `BACKUP_DIR`; существующие файлы не перезаписываются.

```bash
npm run db:offsite-download -- doma-tech-ИМЯ_КОПИИ.sqlite
```

Команда **не восстанавливает базу автоматически**. После успешного скачивания остановите приложение и отдельно выполните стандартное защищённое восстановление:

```bash
ALLOW_DB_RESTORE=true npm run db:restore -- doma-tech-ИМЯ_КОПИИ.sqlite
```

После восстановления перезапустите приложение и проверьте его работу. Для production используйте отдельное зашифрованное хранилище, защищённые credentials rclone и регулярные тестовые восстановления.

В документе описаны первые действия, выбор резервной копии, восстановление, контроль перед возвратом трафика и фиксация фактических RTO/RPO.\n\n### Учебная проверка аварийного восстановления (DR drill)

Изолированный сценарий в `npm run test:db` теперь проверяет полный путь на временных каталогах: создаёт тестовую БД и копию, имитирует внешнее хранилище через mock-rclone, скачивает и проверяет копию, затем восстанавливает её в отдельную намеренно отличающуюся БД. После восстановления тест повторно проверяет SQLite integrity, содержимое таблицы товаров и наличие safety-copy до восстановления. Рабочая база и реальные облачные данные не затрагиваются.

Это автоматизированная проверка логики восстановления, а не подтверждение работоспособности вашего реального облачного аккаунта, сервера, rclone remote или production-процесса. Перед запуском в эксплуатации отдельно проводите контролируемое восстановление на отдельном сервере/стенде, проверяйте реальные бизнес-данные и фиксируйте время восстановления (RTO) и допустимую потерю данных (RPO).

## Автоматический цикл резервирования

Одна команда выполняет локальную резервную копию, проверяет наличие манифеста и при настроенном `OFFSITE_RCLONE_REMOTE` отправляет копию во внешнее хранилище с проверкой чтением обратно:

```bash
npm run db:backup-cycle
```

Результат каждого запуска записывается в `data/backup-operations.jsonl`. При ошибке цикла команда завершается с ненулевым кодом. Если внешний remote не настроен, выполняется только локальная копия. Чтобы требовать обязательную внешнюю копию, задайте `OFFSITE_REQUIRED=true`.

### Контроль состояния резервирования

Проверить последнюю локальную копию, её манифест, SHA-256, целостность SQLite и журнал циклов:

```bash
npm run db:backup-health
```

Проверка выводит JSON со статусом `healthy`, `warning` или `critical`. При критической проблеме возвращается ненулевой код завершения. По умолчанию локальная копия считается устаревшей через 26 часов; настройка — `BACKUP_MAX_AGE_HOURS`. Для внешнего резервирования используются `OFFSITE_MAX_AGE_HOURS` (по умолчанию 50 часов), `OFFSITE_RCLONE_REMOTE` и `OFFSITE_REQUIRED`. Если внешний remote задан, но не обязателен, отсутствие свежей проверенной внешней копии будет предупреждением; при `OFFSITE_REQUIRED=true` — критической ошибкой.

Для ежедневной проверки есть шаблоны `deploy/systemd/doma-tech-backup-health.service` и `deploy/systemd/doma-tech-backup-health.timer`. Таймер запускает проверку в 04:00 (со случайной задержкой до 5 минут), после запланированного цикла резервирования. После адаптации путей установите оба health-unit файла так же, как backup-unit, затем выполните:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now doma-tech-backup-health.timer
systemctl list-timers doma-tech-backup-health.timer
journalctl -u doma-tech-backup-health.service
```

Проверка может отправлять предупреждения и критические ошибки администратору. Поддерживаются Telegram и произвольный HTTPS webhook. Для Telegram укажите в защищённом серверном `.env` обе переменные:

```bash
TELEGRAM_BOT_TOKEN=токен_бота
TELEGRAM_CHAT_ID=идентификатор_чата
```

Либо настройте `BACKUP_ALERT_WEBHOOK=https://ваш-домен/endpoint`. Можно включить оба канала. Не помещайте токены и URL с секретными параметрами в Git, не передавайте их в переписке и не выводите в логи. Отправка ограничена тайм-аутом; сбой уведомления записывается в stderr и не маскирует исходную ошибку резервирования. При нормальном статусе уведомление не отправляется.

Проверка не заменяет внешний мониторинг: если сервер выключен или сам systemd не запускает health-unit, локальный скрипт не сможет сообщить об этом. Для контроля недоступности сервера используйте независимый внешний мониторинг. Шаблоны не активируются автоматически и не подтверждают настройку на сервере.

### Ежедневный запуск через systemd (Linux)

В репозитории есть шаблоны:

- `deploy/systemd/doma-tech-backup.service`
- `deploy/systemd/doma-tech-backup.timer`

Они рассчитаны на установку проекта в `/opt/doma-tech`, системного пользователя и группы `doma-tech`, Node.js/npm в `/usr/bin`, данные в `/opt/doma-tech/data` и резервные копии в `/opt/doma-tech/backups`. Если фактические пути отличаются, отредактируйте unit-файлы до установки. Установите права на каталоги и `.env`, настройте rclone для того же системного пользователя и проверьте ручной запуск.

Пример установки после адаптации путей:

```bash
sudo install -m 0644 deploy/systemd/doma-tech-backup.service /etc/systemd/system/
sudo install -m 0644 deploy/systemd/doma-tech-backup.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now doma-tech-backup.timer
systemctl list-timers doma-tech-backup.timer
```

Таймер запланирован ежедневно на 03:15 по локальному времени сервера с дополнительной случайной задержкой до 15 минут и догоняющим запуском после простоя. Проверяйте историю через `journalctl -u doma-tech-backup.service` и журнал `data/backup-operations.jsonl`.

**Важно:** файлы systemd — шаблоны, они не активируются самим GitHub-коммитом. Установка и настройка на реальном сервере требуют доступа администратора. Не запускайте этот timer на GitHub Pages: Pages не исполняет серверные Node.js процессы.
