# DOMA TECH — план аварийного восстановления (DR runbook)

Документ относится к серверной заготовке в корне репозитория. Опубликованный GitHub Pages сайт — статический прототип: он не использует SQLite, Node.js API или серверные резервные копии.

## 1. Цели и границы

Сценарии: потеря сервера/диска, повреждение SQLite, потеря локальных копий, недоступность внешнего хранилища, компрометация секретов.

RTO и RPO пока не утверждены: фактические значения нужно определить после согласования бизнес-требований и реального теста на целевом сервере. RPO — допустимая потеря данных; RTO — допустимое время восстановления. Технические пороги health-check (26 часов для локальной и 50 часов для внешней копии) не являются гарантией RPO/RTO.

## 2. Первые действия при инциденте

1. Назначьте ответственного и зафиксируйте время обнаружения.
2. При признаках взлома ограничьте публичный доступ на reverse proxy/firewall. Не возвращайте подозрительный сервер в работу.
3. Остановите приложение, чтобы прекратить новые записи и WAL-изменения.
4. Не удаляйте и не перезаписывайте исходную базу, каталоги data/, backups/, uploads/, логи и конфигурацию.
5. Скопируйте доступные материалы инцидента на отдельный защищённый носитель. База может содержать учётные записи и заказы.
6. Выберите последнюю известную исправную копию и согласуйте допустимую потерю данных.

Не выполняйте восстановление, пока приложение может работать или не проверены выбранный файл и возможность отката.

## 3. Сценарий A — приложение недоступно, база сохранна

Проверьте состояние резервирования:

~~~bash
sudo systemctl status doma-tech-backup.service
sudo systemctl status doma-tech-backup-health.service
sudo journalctl -u doma-tech-backup.service --since "24 hours ago"
sudo journalctl -u doma-tech-backup-health.service --since "24 hours ago"
npm run db:backup-health
~~~

Команды npm выполняйте из каталога проекта от пользователя с доступом к файлам. Имя systemd unit приложения в репозитории не задано — выясните фактическое имя. Если резервирование исправно, но API не отвечает, сначала проверьте журналы приложения, конфигурацию, сеть и reverse proxy. Не восстанавливайте базу без признаков её повреждения или потери.

## 4. Сценарий B — повреждение SQLite или ошибочные данные

1. Ограничьте трафик и остановите приложение.
2. Сохраните копию текущего data/doma-tech.sqlite и относящиеся к ней -wal/-shm, если они существуют.
3. Просмотрите резервные копии и состояние:
   ~~~bash
   ls -lah backups/
   npm run db:backup-health
   ~~~
4. Выберите копию, созданную до инцидента. Сверьте время, манифест, хеш и ожидаемую потерю данных.
5. Если копии нет локально, скачайте её из внешнего хранилища (раздел 6).
6. Выполните восстановление по разделу 6.2.

Не считайте самый новый файл автоматически лучшим.

## 5. Сценарий C — полная потеря сервера или диска

1. Подготовьте чистый сервер с Node.js 20+, Git и rclone, если используется внешняя копия.
2. Получите репозиторий из доверенного источника и проверьте ветку/коммит.
3. Установите зависимости командой npm ci.
4. Восстановите секреты из защищённого хранилища или создайте новые. Не копируйте секреты с подозрительного сервера.
5. Восстановите конфигурацию rclone для зашифрованного remote.
6. Создайте каталоги данных и резервных копий с минимальными правами доступа.
7. Скачайте и проверьте внешнюю копию.
8. Восстановите базу по разделу 6.2.
9. Отдельно восстановите uploads/ из проверенной копии, если там есть пользовательские изображения. SQLite backup не включает uploads/.
10. Запустите приложение на закрытом тестовом адресе и выполните проверки раздела 7.
11. Переключайте reverse proxy/DNS только после одобрения ответственного.

## 6. Скачивание и восстановление базы

### 6.1 Скачать внешнюю копию

Настройте OFFSITE_RCLONE_REMOTE и доступ rclone к тому же зашифрованному remote.

~~~bash
npm run db:offsite-download -- ИМЯ_КОПИИ.sqlite
~~~

Скрипт скачивает манифест и SQLite во временный каталог, сверяет SHA-256 и целостность SQLite, затем копирует пару в локальный BACKUP_DIR. Существующие файлы не перезаписываются. Команда не восстанавливает рабочую базу.

### 6.2 Восстановить выбранную копию

Для systemd используйте фактическое имя unit приложения. Например, если он действительно называется doma-tech.service:

~~~bash
sudo systemctl stop doma-tech.service
sudo systemctl is-active doma-tech.service
~~~

Убедитесь, что приложение и все процессы с открытой SQLite остановлены. Пример имени unit условный: такого unit-файла в текущих шаблонах репозитория нет.

Файл резервной копии и JSON-манифест должны находиться в BACKUP_DIR. Выполните из каталога проекта:

~~~bash
ALLOW_DB_RESTORE=true npm run db:restore -- ИМЯ_КОПИИ.sqlite
~~~

Скрипт проверяет манифест, SHA-256, целостность SQLite и обязательные таблицы; создаёт safety-copy текущей базы; проверяет staged-файл; удаляет старые WAL/SHM и заменяет файл базы.

**Ограничение:** текущий скрипт требует, чтобы рабочая база уже существовала, а каталог резервных копий был доступен. На полностью новом сервере без data/doma-tech.sqlite он остановится. Первичное восстановление на чистом сервере требует отдельной проверенной процедуры; не создавайте вручную пустую production-БД.

Safety-copy имеет специальное имя и не подходит под формат обычных backup-файлов для offsite-скрипта. Сохраните её отдельно, если она нужна для отката.

## 7. Проверки до возвращения трафика

1. SQLite открывается, PRAGMA integrity_check возвращает ok.
2. Существуют таблицы admins, products, orders и sessions.
3. Проверены ожидаемые товары и заказы по контрольным данным.
4. Проверены права доступа к data/, uploads/ и backups/.
5. На закрытом адресе проверены /api/health, каталог и критические административные функции.
6. Секреты обновлены, доступы и сессии не скомпрометированы.
7. Тестовый заказ выполняется только в согласованном тестовом режиме.
8. Зафиксированы время восстановления и последняя доступная точка данных.
9. Публичный трафик возвращается только после решения ответственного.

## 8. Сценарий D — внешнее хранилище недоступно

- Не удаляйте локальные копии и не меняйте remote вслепую.
- Проверьте сеть, конфигурацию rclone и права доступа.
- Не вставляйте ключи и токены в тикеты, GitHub или логи.
- Если локальная база исправна, продолжайте работу только в рамках утверждённого риска.
- Если локальные копии потеряны, не обещайте восстановление до подтверждения независимой копии.
- После восстановления связи скачайте копию и повторите проверки манифеста, хеша и SQLite.

## 9. Сценарий E — компрометация секретов или сервера

1. Изолируйте сервер и сохраните журналы для расследования.
2. С доверенного устройства замените пароль администратора, SESSION_SECRET, токены Telegram, webhook credentials и доступы к облаку, если они могли быть раскрыты.
3. Проверьте целостность и происхождение резервных копий. SHA-256 рядом с копией обнаруживает повреждение, но не доказывает подлинность, если злоумышленник мог изменить и базу, и манифест.
4. Выберите копию, заведомо предшествующую компрометации, и восстановите её на чистой инфраструктуре.
5. Пересоздайте сессии и секреты; проверьте учётные записи и журналы до возврата трафика.

## 10. После инцидента

Зафиксируйте:
- время обнаружения и восстановления;
- причину и затронутые компоненты;
- имя копии, время создания и SHA-256;
- фактическую потерю данных (RPO) и длительность восстановления (RTO);
- результаты проверок;
- заменённые секреты и защитные меры;
- задачи по предотвращению повторения.

После закрытия инцидента создайте новую локальную и внешнюю копию, проверьте их и назначьте повторный DR drill.

## 11. Эксплуатационные ограничения

- GitHub Pages — статический прототип, он не восстанавливается из SQLite.
- systemd-файлы — шаблоны, требующие адаптации, установки и проверки на целевом Linux-сервере.
- Реальные сервер, rclone remote, Telegram/webhook и облачные учётные данные этим документом не настраиваются.
- SQLite backup не включает uploads/, .env, reverse proxy, TLS-сертификаты или systemd overrides. Для них нужны отдельные защищённые копии.
- Автоматизированный DR drill использует временные каталоги и mock-rclone. Он проверяет как восстановление существующей БД, так и первоначальную установку копии при отсутствии рабочей БД. Он не заменяет восстановление на реальном резервном сервере.
